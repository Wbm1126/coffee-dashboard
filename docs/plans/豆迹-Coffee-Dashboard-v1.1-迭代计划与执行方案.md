# 豆迹 Coffee Dashboard v1.1 迭代计划与执行方案

> 版本定位：**可用性重构**
>
> 核心目标：先把历史咖啡记录完整迁入豆迹，再把“新咖啡豆添加 + 评测”重构成一个真正适合日常使用的低摩擦流程。  
> 本版本不追求增加更多复杂功能，而是让已有产品从“功能齐全”变成“愿意每天使用”。

---

## 1. 当前问题

v1.0 已完成本地数据存储、历史 Excel 导入、咖啡豆档案、购买 / 饮用 / 评价、联网采集、推荐、比较、导出等完整能力，但真实使用中仍存在三个关键问题：

1. **历史记录没有完整进入系统**
   - 现有导入逻辑高度绑定最初的两份 Excel 结构。
   - 历史记录可能缺少准确日期、冲煮方式等字段，当前数据模型不够自然地表达这些旧数据。
   - 历史数据不完整，导致后续咖啡库、推荐、比较、个人偏好分析都缺少基础。

2. **新增咖啡豆流程过于复杂**
   - 当前联网流程为：搜索 → 选择网页 → 解析 → 字段逐项确认 → 创建 / 合并。
   - 用户实际上只希望输入**咖啡豆名称**或**商品链接**，系统自动补齐绝大多数商品资料。
   - 用户只应该负责修正错误信息，以及填写自己的饮用体验和评价。

3. **产品结构仍偏向“功能展示”而非“日常使用”**
   - 首页功能过多且纵向堆叠。
   - 高频动作入口不够突出。
   - 商品图片、当前在喝、最近评测、快速记录等更有日常价值的信息展示不足。

---

# 2. v1.1 版本目标

v1.1 只围绕以下四个结果展开。

## 2.1 历史数据完整迁移

用户现有历史咖啡记录可以完整进入豆迹。

允许历史数据存在：

- 无准确饮用日期
- 无完整冲煮参数
- 只有个人评分 / 文字评价
- 只有美式或奶咖其中一个评价
- 字段名称和当前系统不一致
- 同一咖啡豆多次历史记录
- 与当前数据库已有豆重复

系统不得为了满足 schema 而伪造不存在的数据。

---

## 2.2 新咖啡豆 30～60 秒完成入库

用户只需要提供以下任意一种输入：

- 咖啡豆名称
- 品牌 + 咖啡豆名称
- 商品链接
- 一段复制来的商品介绍文本

系统应尽量自动获取：

- 品牌
- 商品名
- 商品图片
- 烘焙度
- 处理法
- 国家 / 产区 / 庄园 / 品种
- 官方风味描述
- 风味标签
- 规格
- 参考价格
- 商品来源链接

用户只负责：

1. 检查系统自动填充结果
2. 修正错误
3. 保存
4. 按需填写个人评测

---

## 2.3 评测流程低摩擦

默认使用“快速评价”。

日常记录一杯咖啡时，不应要求用户一次填写所有信息。

默认只需要：

- 咖啡豆
- 饮用方式
- 评分
- 简短感受

其他内容按需展开：

- 萃取参数
- 风味标签
- 优点
- 缺点
- 回购判断
- 综合评价
- 详细品鉴

---

## 2.4 页面从“功能集合”变成“个人咖啡工具”

重点优化：

- 首页
- 咖啡库
- 咖啡豆详情
- 新增咖啡豆
- 评测录入

同时补充：

- 商品图片
- 最近喝过
- 当前在喝
- 最近新增
- 待评价
- 快捷操作

---

# 3. 本版本产品原则

开发过程中优先遵守以下原则。

## 3.1 少填信息优先

能够自动获取的信息不要要求用户填写。

能够以后补充的信息不要阻塞当前保存。

---

## 3.2 数据真实性优先

历史数据缺少某字段时保存为未知 / 空值。

不得：

- 伪造历史日期
- 伪造冲煮方式
- 根据推测直接覆盖用户记录

---

## 3.3 自动化结果必须可修正

任何自动抓取字段都必须允许用户修改。

自动数据需要保留来源信息，继续使用现有 provenance 设计。

---

## 3.4 自动失败不能阻塞添加

搜索失败、网页无法抓取、动态页面无法解析时：

> 用户仍然必须能够立即手工创建咖啡豆。

最低创建要求保持：

- 品牌
- 豆名

---

## 3.5 保留当前优秀基础设施

v1.1 不重写以下基础：

- React
- Fastify
- TypeScript
- Local First
- 本地 JSON Repository
- dataRevision
- 原子写入
- 自动备份
- Recovery Mode
- provenance
- Markdown / PDF 导出
- 当前购买 / 饮用事实模型

除非实现新需求必须调整，否则不要进行无收益的底层技术迁移。

---

# 4. 数据模型升级：Schema v2

当前 `schemaVersion = 1`。

v1.1 升级至：

```text
schemaVersion = 2
```

升级必须带完整 migration。

---

## 4.1 新增 BeanEvaluation

新增独立的咖啡豆评价事实，不要求评价必须依附某一次 DrinkingRecord。

建议语义：

```text
BeanEvaluation
- id
- beanId
- source
- evaluatedOn?
- brewMethod?
- americanoReview?
- milkReview?
- overallScore?
- flavorNotes[]
- pros?
- cons?
- summary?
- repurchase?
- sourceRecordId?
- createdAt
- updatedAt
```

`source` 至少支持：

```text
manual
drinking
legacy_import
```

用途：

- 导入没有准确饮用日期的历史评价
- 保存历史个人评分
- 保存旧笔记
- 避免为了兼容数据模型伪造 DrinkingRecord

---

## 4.2 冲煮参数结构化

保留现有 `extractionNote`，同时增加可选结构化参数：

```text
doseGrams
yieldGrams
brewTimeSeconds
temperatureC
grindSetting
waterGrams
milkGrams
```

所有字段均 optional。

目的：

- 快速复用上次配方
- 后续做个人冲煮参数分析
- 避免所有参数长期埋在自由文本中

---

## 4.3 商品图片

CoffeeBean 或 ProductSource 增加图片信息。

建议支持：

```text
imageUrl
localImagePath?
imageSource?
```

优先策略：

1. 抓取公开商品图
2. 下载后本地缓存
3. 保存来源 URL
4. 图片获取失败不影响咖啡豆创建

不得把图片变成核心保存依赖。

---

# 5. 开发阶段

---

# Phase 1 — 历史记录迁移

**优先级：P0**

这是 v1.1 的第一阶段，完成前不要优先投入推荐算法或其他附加功能。

## 5.1 建立 Migration Center

替换当前高度绑定两份固定 Excel 的导入体验。

新的导入中心应完成：

```text
上传历史记录
      ↓
识别文件 / 工作表
      ↓
识别字段
      ↓
映射到豆迹字段
      ↓
数据标准化
      ↓
重复识别
      ↓
冲突预览
      ↓
用户确认
      ↓
写入数据库
```

---

## 5.2 第一目标不是“支持所有格式”

不要一开始开发庞大的通用 ETL 系统。

首先保证：

> 用户当前真实持有的历史咖啡记录能够完整导入。

在此基础上保留可扩展的 importer / mapper 接口。

建议支持：

- XLSX
- CSV

JSON / Markdown 等格式可以预留接口，但不作为 v1.1 必须项。

---

## 5.3 字段自动映射

Importer 应能够识别常见同义字段，例如：

```text
豆名 / 咖啡豆 / 商品名
品牌 / 烘焙商
处理法 / 处理方式
烘焙 / 烘焙度
风味 / 风味描述 / 风味标签
评分 / 个人评分 / 综合评分
美式 / 美式表现
奶咖 / 奶咖表现
备注 / 评价 / 感受
回购 / 是否回购
```

用户可以手动修改映射结果。

---

## 5.4 重复识别

优先使用：

```text
normalized brand + normalized bean name
```

识别：

- 新豆
- 已存在
- 可能重复
- 同豆多次评价

不要因为一条豆有多次历史评价而错误去重掉评价记录。

---

## 5.5 导入预览

提交前至少显示：

- 新增咖啡豆数量
- 合并咖啡豆数量
- 新增评价数量
- 可能重复数量
- 冲突数量
- 无法识别记录

只有真实冲突才需要用户参与。

格式差异应尽量自动归一化。

---

## 5.6 历史迁移验收

完成标准：

- 用户现有历史咖啡豆全部进入系统
- 用户历史评分全部保留
- 文字评价全部保留
- 无日期记录可以正常存在
- 重复导入不会生成重复数据
- 原始文件不被修改
- 导入前自动备份
- 导入失败整批回滚

---

# Phase 2 — 新增咖啡豆流程重构

**优先级：P0**

现有 `CollectionWizard` 不再作为主要交互形态。

核心入口统一为：

```text
+ 添加咖啡豆
```

---

## 6.1 单一输入入口

用户进入添加页面后首先只看到一个主输入框：

```text
输入咖啡豆名称、商品链接，或粘贴商品介绍
```

系统自动判断输入类型。

---

## 6.2 名称输入

例如：

```text
乔治队长 草莓糖
```

系统直接执行搜索并整理候选商品。

候选卡片优先展示：

- 图片
- 品牌
- 豆名
- 烘焙度
- 处理法
- 风味
- 规格
- 价格
- 来源

用户选择正确候选后进入确认。

不要再要求：

```text
搜索
→ 查看网页结果
→ 点击解析链接
```

搜索和解析应在系统内部自动完成。

---

## 6.3 商品链接输入

用户粘贴链接后：

```text
URL
 ↓
安全检查
 ↓
页面抓取
 ↓
商品字段提取
 ↓
图片提取
 ↓
重复检测
 ↓
确认页面
```

尽量做到一次完成。

---

## 6.4 文本粘贴输入

支持用户从淘宝、微信、小红书、烘焙商页面等复制商品描述。

例如：

```text
乔治队长 草莓糖
埃塞俄比亚
日晒
中浅烘
草莓、红糖、奶油
250g 98元
```

系统自动整理字段。

这个入口用于解决：

- 网页反爬
- 登录页面
- 动态渲染
- 微信 / 小红书等无法直接抓取页面

---

## 6.5 确认页面

自动采集后，只展示一个简洁的资料确认表。

区分：

### 自动获取

- 商品图片
- 品牌
- 豆名
- 烘焙度
- 处理法
- 产地
- 品种
- 风味
- 官方描述
- 规格
- 价格

### 用户个人信息

- 是否已购买
- 是否正在喝
- 个人感受
- 评分
- 是否回购

默认只展开商品信息。

个人评价可以：

```text
现在填写
稍后填写
```

---

## 6.6 创建规则

只要存在：

```text
品牌
+
豆名
```

即可保存。

其他字段全部 optional。

自动信息不完整不能阻止保存。

---

# Phase 3 — 联网采集 V2

**优先级：P0**

当前 DuckDuckGo HTML + 通用正则解析只能作为 fallback，不应继续作为唯一核心方案。

---

## 7.1 Provider 架构

把搜索能力抽象为：

```text
SearchProvider
```

统一输出：

```text
title
url
snippet
image?
source
```

具体搜索来源可替换。

UI 不依赖某一个 Provider。

---

## 7.2 Product Extractor

统一输出标准商品数据：

```text
brand
name
image
roastLevel
process
country
region
farm
variety
flavorNotes
officialDescription
packageGrams
price
currency
sourceUrl
```

字段不存在允许为空。

---

## 7.3 抽取优先级

按以下层级处理。

### Level 1 — 结构化页面数据

优先：

- JSON-LD Product
- OpenGraph
- meta
- 页面标准结构化字段

### Level 2 — 通用页面正文解析

从正文识别咖啡领域字段。

### Level 3 — Site Adapter

对高频烘焙商 / 商城实现定向适配器。

Adapter 必须是增量增强，不允许把主流程写死到某一家网站。

### Level 4 — 手工 / 文本回退

页面抓取失败时直接回退至文本解析或最小手工创建。

---

## 7.4 来源和可信度

自动字段继续使用 provenance。

建议额外记录：

```text
source
confidence
capturedAt
```

如果多个来源对同一字段存在冲突：

- 不静默覆盖用户确认值
- 用户值优先
- 已确认值默认保留
- 新来源作为候选显示

---

## 7.5 实际联网验收

v1.1 不允许只通过 fixtures 判断“联网采集完成”。

必须增加真实 smoke test。

至少覆盖：

- 普通静态商品页
- 带 JSON-LD 商品页
- 一个中文咖啡烘焙商商品页
- 页面字段不完整
- 页面无法抓取
- 429
- 超时
- 动态页面
- 无商品字段

真实抓取失败时必须证明：

> 用户仍然可以顺利完成添加。

---

# Phase 4 — 快速评测重构

**优先级：P1**

---

## 8.1 快速评价模式

默认流程：

```text
选择咖啡豆
   ↓
选择喝法
   ↓
评分
   ↓
一句感受
   ↓
保存
```

目标：

> 30～60 秒完成一杯咖啡的记录。

---

## 8.2 根据喝法只显示当前评价

如果用户本次选择：

```text
奶咖
```

默认只显示奶咖评价。

不要同时要求填写美式。

美式评价可以未来独立补充。

---

## 8.3 高级评价

通过“展开详细记录”显示：

- 风味标签
- 优点
- 缺点
- 详细品鉴
- 是否回购
- 综合等级
- 萃取参数
- 牛奶 / 加水量

---

## 8.4 配方复用

咖啡豆详情页显示：

```text
上次冲煮

18g → 36g
29s
牛奶 220g
奶咖 4.5
```

提供：

```text
照上次再来一杯
```

自动预填上一条参数。

---

# Phase 5 — 页面与展示优化

**优先级：P1**

不要求重新设计整个视觉体系。

重点解决信息架构和高频入口。

---

## 9.1 一级导航

建议重构为四个核心区域：

```text
首页
咖啡库
记录
添加
```

推荐、导出、历史迁移等功能作为二级能力存在。

---

## 9.2 首页

首页重点显示：

### 当前在喝

当前已开封 / 最近频繁饮用的咖啡豆。

### 最近喝过

最近饮用记录。

### 待评价

已记录饮用但未完成评价的豆。

### 快捷操作

```text
+ 添加咖啡豆
☕ 记录一杯
★ 写评价
```

### 最近新增

最近加入咖啡库的豆。

---

## 9.3 咖啡库

保留现有：

- 搜索
- 筛选
- 排序
- 卡片 / 列表
- 比较
- 详情

增强：

- 商品图片
- 当前状态
- 最近评分
- 最近喝法
- 最佳 / 最近配方
- 回购判断

---

## 9.4 咖啡豆详情

重新整理信息优先级：

```text
商品信息
↓
我的评价
↓
最近冲煮
↓
历史记录
↓
购买记录
↓
数据来源
```

默认不要把技术性的 provenance 细节放在主要视觉区域。

---

# Phase 6 — 稳定性、迁移与发布

**优先级：P0**

---

## 10.1 Schema Migration

v1 → v2 必须做到：

- 自动备份 v1 数据
- 自动执行 migration
- migration 可重复测试
- migration 失败进入只读 / recovery
- 不允许部分升级

---

## 10.2 数据兼容

v1 现有：

- beans
- purchases
- drinkingRecords
- assessments
- productSources

必须完整保留。

已有数据不得因为新模型重构而丢失。

---

## 10.3 测试重点

测试资源优先放在真实高风险流程。

必须覆盖：

1. v1 → v2 migration
2. 历史文件批量导入
3. 重复导入
4. 历史评价无日期
5. 名称搜索创建咖啡豆
6. URL 创建咖啡豆
7. 文本粘贴创建咖啡豆
8. 联网失败后手工创建
9. 商品图片失败
10. 快速评价
11. 结构化冲煮参数
12. revision 冲突
13. backup / recovery

---

# 11. 本版本暂不重点开发

以下能力保留现状，但本版本不要投入大量开发时间：

- 推荐算法升级
- 云同步
- 用户账号
- 多用户
- 移动 App
- 社区系统
- 自动下单
- 价格长期监控
- AI 聊天功能
- 大规模数据库迁移
- SQLite 重构
- 新 PDF 能力
- 新导出格式

除非新功能开发必需，否则不要顺手重构这些模块。

---

# 12. 推荐执行顺序

严格优先完成数据和核心日常流程。

```text
U1 Schema v2 + migration
        ↓
U2 历史记录完整迁移
        ↓
U3 新增咖啡豆统一入口
        ↓
U4 搜索 / URL / 文本自动采集
        ↓
```

# 14. v1.1 最终验收标准

版本可以发布必须满足以下条件。

## 历史数据

- 用户现有历史咖啡豆全部完成迁移
- 历史评价无丢失
- 无日期数据不伪造日期
- 导入前有备份
- 重复导入不重复创建

## 新增咖啡豆

用户提供：

```text
咖啡豆名称
```

或：

```text
商品链接
```

系统可以自动生成可确认的咖啡豆资料。

用户主要工作只剩：

```text
检查
修正
保存
```

## 评价

普通一次评测不需要填写完整长表单。

快速模式可以在 30～60 秒内完成。

## 联网失败

任何搜索 / 抓取失败场景均不得导致用户无法创建咖啡豆。

## 图片

能抓取商品图片时自动显示。

无法抓取时正常使用默认占位图。

## 数据安全

- 所有旧数据保留
- schema migration 有备份
- revision 机制正常
- recovery 正常

# 15. 给 Codex 的实现要求

1. **先阅读现有仓库和本文件，再开始修改。**
2. 不要推倒当前架构重写。
3. 优先复用现有 domain / repository / provenance / backup 能力。
4. 不要为了技术洁癖进行与 v1.1 目标无关的大重构。
5. 每完成一个 Unit 都应保持项目可以启动和测试。
6. Schema 改动必须同时提交 migration 和测试。
7. 自动采集一定保留手工 fallback。
8. 自动抓取数据不能覆盖用户已经确认的数据。
9. 产品交互优先减少步骤，不要因为内部技术流程增加用户操作。
10. 遇到实现细节未明确时，以本文件中的**产品目标和原则**自行做合理决策，不需要把每个 UI 细节硬编码成这里的示例。

# 16. Definition of Done

v1.1 真正完成的标志不是“新增了多少功能”，而是以下三个日常场景已经顺畅：

### 场景 A：导入过去

```text
把旧记录导入
→ 检查冲突
→ 全部进入咖啡库
```

### 场景 B：买了一支新豆

```text
输入豆名 / 粘贴链接
→ 自动获取商品资料和图片
→ 修正错误
→ 保存
```

### 场景 C：早上喝完一杯

```text
打开豆迹
→ 选择咖啡豆
→ 选择喝法
→ 打分
→ 写一句感受
→ 保存
```

如果这三个场景不再让用户觉得“麻烦”，v1.1 才算完成。
